# SDKs and CLI

Two surfaces, one contract.

| Artefact | Location | Status |
| --- | --- | --- |
| Python package `parsedock` (hand-written lifecycle wrapper) | `sdk/python` | **on PyPI**: `pip install parsedock==0.1.1`; `parsedock` console script, version-checked |
| Generated Python client | `sdk/python-generated` | machine-readable surface, regenerated by `make sdk` |
| Generated Java client `com.luxiangs:parsedock-client` | `sdk/java-generated` | **on Maven Central** (`com.luxiangs:parsedock-client:0.1.1`); builds with Maven (`mvn -f sdk/java-generated/pom.xml package`) |

The generated clients mirror `api/openapi.yaml`; the hand-written Python wrapper encodes the
lifecycle rules that an OpenAPI document cannot express.

## Using the SDKs

### Python

```bash
pip install parsedock==0.1.1     # or: pip install -e sdk/python
```

```python
from parsedock_sdk import ParseDockClient, ParseDockError

with ParseDockClient("http://localhost:8080", token=TOKEN) as c:
    job = c.create_job("invoice.pdf", mode="auto", idempotency_key="invoice-42")
    final = c.wait(job["job_id"], timeout=600)
    if final["status"] != "completed":
        raise SystemExit(final.get("error_code"))
    md, version = c.download(job["job_id"], fmt="markdown")   # bytes, result_version
    ir, _ = c.download(job["job_id"], fmt="json")             # Document IR
    c.ack(job["job_id"], version)                             # release the server copy
    c.wait_released(job["job_id"])
```

Other entry points: `download_and_ack(..., sink=...)` (ACK only after your sink
returns), `parse_sync(path)` (small files), `events(job_id, last_event_id=...)`
(SSE, resumable), `cancel(job_id)`. Errors are `ParseDockError(status, code,
message)` with `.retryable`; the wrapper retries retryable failures with backoff.

The retry rule is code-first, not status-first: `quota_exceeded` shares the `429`
status with `rate_limited` but is **not** retryable — the quota only resets when
its rolling window passes — and the server's `Retry-After` is honoured.
`create_job` always sends an `Idempotency-Key` (yours, or a generated one), so a
retried upload whose first response was lost replays instead of creating a second
job. `wait_released` raises `TimeoutError` rather than reporting a release that
has not happened, and `download_and_ack(sink=...)` requires the sink to have
*durably* stored the bytes when it returns (a buffered write that is never closed
does not qualify).
`docs/ERROR-CODES.md` lists the codes; `.agents/skills/parsedock-python-sdk/` is a
condensed version for agent use (see "Agent skills" below).

### Java

```bash
# from Maven Central (dependency below), or build the current client from the repository:
mvn -f sdk/java-generated/pom.xml -DskipTests install
```

```xml
<dependency>
  <groupId>com.luxiangs</groupId>
  <artifactId>parsedock-client</artifactId>
  <version>0.1.1</version>
</dependency>
```

```java
ApiClient client = new ApiClient();
client.setBasePath("http://localhost:8080");
client.setBearerToken(System.getenv("PARSEDOCK_TOKEN"));
JobsApi api = new JobsApi(client);

// (file, mode, device, ttlSeconds, priority, idempotencyKey, + the query mirror
// of the same fields: pass nulls)
Job job = api.createJob(new File("invoice.pdf"), "auto", "auto",
        null, null, null, null, null, null, null);
Job done;
do {
    Thread.sleep(300);
    done = api.getJob(job.getJobId());
} while (done.getStatus() == Job.StatusEnum.QUEUED
        || done.getStatus() == Job.StatusEnum.RUNNING);

String markdown = api.downloadResult(done.getJobId(), "markdown");
DocumentIR ir = JSON.deserialize(api.downloadResult(done.getJobId(), "json"), DocumentIR.class);
api.ackJob(done.getJobId(),
           new AckJobRequest().resultVersion(done.getResultVersion()), null);
```

Failures throw `ApiException` (`getCode()` = HTTP status). The generated client
has **no retry policy**: back off on `429 rate_limited` and 5xx, never on the
other 4xx codes. The loop above is the shortest form: production code needs a deadline
and should treat any status other than `COMPLETED` (including `UNKNOWN_DEFAULT_OPEN_API`,
a status this client version does not know) as "no result". `downloadResult` holds the
whole body in a `String`; stream large results with `downloadResultCall(...).execute()`
(the skill has the snippet). `sdk/java-client-test` is a worked example (JUnit, runs against a
live server):

```bash
mvn -f sdk/java-client-test/pom.xml test \
  -Dparsedock.base=http://localhost:8080 -Dparsedock.token=$PARSEDOCK_TOKEN \
  -Dparsedock.fixture=path/to/file.pdf
```

`.agents/skills/parsedock-java-sdk/` is the condensed version for agent use.

## Agent skills

`.agents/skills/parsedock-python-sdk/` and `.agents/skills/parsedock-java-sdk/` are written
for projects that *call* a deployed ParseDock, and each directory is self-contained: copy
it into another repository's skills folder (for example `.claude/skills/`) and it works
offline. `SKILL.md` links only into its own `references/`:

| File | Generated from |
| --- | --- |
| `references/error-codes.md` | `docs/ERROR-CODES.md` (the code table, without the internal "Origin" column) |
| `references/document-ir.md` | `docs/DOCUMENT-IR.md` §2 and §2a |
| `references/openapi.yaml` | `api/openapi.yaml` |

`python3 scripts/sync_skills.py` regenerates them; `--check` (static CI phase) fails when
they are stale, when a `SKILL.md` names a repository path or make target, or when its
"Applies to ParseDock API `X.Y`" line disagrees with `api/openapi.yaml`. Text in the
source documents between `<!-- skill:omit -->` and `<!-- /skill:omit -->` is
repository-internal and stays out of the copies. Building or testing the SDKs from this
checkout (`make sdk`, `mvn -f sdk/java-generated/pom.xml install`, `sdk/java-client-test`)
is documented here, not in the skills.

## Runnable examples

Two minimal projects that parse one document, write the result and only then ACK:

```bash
export PARSEDOCK_TOKEN=...          # key from deploy/.env (PARSEDOCK_API_KEYS)

cd examples/python && make run      # pip installs the SDK into examples/python/.venv
cd examples/java   && make run      # mvn installs the generated client, then exec:java
```

`FILE=… MODE=accurate` selects other inputs and modes; output lands in
`examples/*/out/`. `scripts/sdk-check.sh` runs both against a live stack on every
nightly, so they cannot rot. Neither sets an idempotency key: re-running must not
replay an already-released job.

## Lifecycle rules the wrapper enforces

1. **ACK only after your sink succeeded.** `download_and_ack(job_id, sink=...)` writes the
   bytes first and only then releases the result. A failing sink leaves the result
   available for retry — tested by `sdk/python/test_sdk.py`.
2. **ACK requires the `result_version`** returned by the download (or from the job view);
   a stale version is refused with `409`. `cancel` never releases a result: on a
   completed job it returns `409` and points at ACK.
3. **ACK is idempotent**; repeating it never resurrects a released result.
4. **`410 Gone` after ACK** is the expected outcome, not an error to retry.
5. **Status polling shares the per-owner rate budget.** Use the SSE stream
   (`client.events(job_id)`) for waits longer than a few seconds, or raise `--rate-limit`;
   `parsedock_throttled_total{reason="rate_limited"}` shows when a client is polling too
   hard (RC-5, `docs/SLO.md`).

## CLI

```bash
pip install parsedock==0.1.1       # or: uv pip install parsedock==0.1.1
export PARSEDOCK_TOKEN=…           # or --token

parsedock parse ./invoice.pdf -o out.md                 # markdown, ACK on success
parsedock parse ./invoice.pdf --format json -o out.json
parsedock parse ./scan.pdf --mode accurate --device gpu_required --keep
parsedock status job_06GRV…
parsedock --version
```

Exit codes: `0` success, `1` the job ended `failed`/`cancelled` (details on stderr), `2`
usage or connection error. `--keep` leaves the result downloadable (no ACK) so you can
inspect it, then release it yourself.

## Versioning

`scripts/check_versions.py` asserts that the binary (`--version`, JSON), `api/openapi.yaml`
`info.version`, `sdk/python` (`__version__` **and** `pyproject.toml`) and the Java `pom.xml`
all carry the same version. `scripts/sdk-check.sh` runs that plus the Python end-to-end
lifecycle test, the CLI smoke run and the Maven build:

```bash
make sdk-check                     # everything
bash scripts/sdk-check.sh --fast   # what CI runs on every PR (no Java, no engines)
```

### What is tested, and against what

Every layer below starts a **real `docparse` process** and talks HTTP; none of it
stubs a server.

| Layer | Script | Engine | Covers |
| --- | --- | --- | --- |
| lifecycle | `sdk/python/test_sdk.py` | `mock` | create → wait, idempotent replay, SSE, both downloads, stale ACK 409, failing sink does not release, ACK → 410 → released, repeat ACK, cancel, sync parse, CLI (exit codes, `--keep`) |
| error matrix | `sdk/python/test_sdk_matrix.py` | `mock` | `rate_limited` 429 + client backoff, `quota_exceeded` **not** retried, `file_too_large` 413, `encrypted_file` 422, `gpu_unavailable` 409, `not_found` 404, SSE resume from `Last-Event-ID` without replay |
| real engines | `sdk/python/test_sdk_real.py` | `xberg` | IR schema, elements, `routing.actual_device` vocabulary, warning codes, table grids, ACK/410, and a scanned PDF carrying `ocr_used` (skips if xberg/tesseract are absent) |
| java client | `sdk/java-client-test` | `mock` (PR) / `xberg` (nightly) | generated client: auth, multipart upload, poll, both downloads deserialised into the generated `DocumentIR` model (schema, elements, routing, warnings, table grids), stale ACK 409, ACK → 410, unknown job 404 |

CI wiring: the `sdk` job in `ci.yml` runs `--fast` on every PR (so an OpenAPI or IR
change cannot silently break a client), and the nightly `sdks` job runs the full
set with real engines and the Java integration test.

Known gaps: no `schemathesis` property-based fuzzing,
no async client, and the Java client is generated (its integration test lives in
`sdk/java-client-test` so regeneration cannot delete it).

## Publishing status

| Registry | Coordinate | State |
| --- | --- | --- |
| **PyPI** | `parsedock==0.1.1` (and `0.1.0`) | wheel + sdist, Apache-2.0, published by `release-python.yml` on the `v0.1.1` tag |
| **Maven Central** | `com.luxiangs:parsedock-client:0.1.1` (and `0.1.0`) | jar + sources + javadoc, GPG-signed, uploaded by `release-maven.yml`; each release needs the one-click **Publish** in the [Central Portal](https://central.sonatype.com/publishing/deployments) (`autoPublish=false` on purpose) |

Both are produced from the same version and gated by `.github/workflows/release-python.yml`
(PyPI, Trusted Publishing/OIDC, no token) and `release-maven.yml` (Central, GPG-signed,
sources + javadoc jars). The procedure, the required secrets, the namespace rules and the
failures we hit are in [`docs/RELEASING.md`](RELEASING.md).

The generated `parsedock_client` package stays **repo-only**: one distribution, one
version, no second thing to keep in sync.

## Not delivered (honest gap)

* **Container images** are not pushed to a registry.
* **`schemathesis` property-based contract testing.** The repo has 47 contract checks
  generated from the OpenAPI document plus a live end-to-end SDK test; property-based
  fuzzing of every endpoint is the natural next step and needs a pinned schemathesis
  version in the nightly job rather than a new dependency in the PR path.
* **Async client.** Not implemented, and the package declares no `async` extra; SSE and
  `wait()` are synchronous today (run them in a thread from async code).
